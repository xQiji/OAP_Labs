Лабораторна робота №5: Безпека веб-додатків
Цей проєкт демонструє захист веб-додатка (Node.js/TypeScript + Vanilla JS) від поширених вразливостей згідно з OWASP Top 10. Реалізовано всі 4 сценарії захисту (А, Б, В, Г) для отримання максимального балу.

Архітектурні рішення безпеки (Відповідність вимогам)
Бекенд на TypeScript: Типізація допомагає уникати помилок на етапі розробки.

Єдині правила авторизації: Перевірка користувача винесена в окремий authMiddleware. Логіка не дублюється в кожному роуті.

Централізована обробка помилок: Усі помилки (включно з помилками безпеки) обробляються глобальним middleware і повертаються клієнту в єдиному узгодженому форматі { code, message } (через клас ApiError). Жодних "stack trace" у відповідях сервера.

Принцип найменших привілеїв: Користувач має доступ виключно до своїх ресурсів.

Security Regression: Відтворення та Виправлення (Було / Стало)

Сценарій В: Insecure Direct Object Reference (IDOR)
Суть вразливості: Відсутність перевірки прав власності (Access Control) на сервері. Будь-який авторизований користувач міг видалити або змінити ресурс іншого користувача, підставивши його ID.

Як відтворити (PoC): Відправити HTTP-запит DELETE /api/tickets/1 із заголовком X-Demo-UserId: 2 (спроба Користувача 2 видалити заявку Користувача 1).

Було (До виправлення): Сервер успішно видаляв чужу заявку (Статус 200/204).

Стало (Після виправлення): Перевірка власника додана на кожну чутливу операцію (Update, Delete). SQL-запит містить умову WHERE id = ? AND authorId = ?. Сервер повертає стандартизовану помилку 403 Forbidden / 404 Not Found.

Сценарій Г: Security Misconfiguration (Харднінг)
Було (До виправлення): Сервер використовував небезпечний CORS (Access-Control-Allow-Origin: *) та не мав базових заголовків безпеки, що дозволяло атаки типу Clickjacking.

Стало (Після виправлення): 1. CORS обмежено до конкретного origin фронтенду (наприклад, 127.0.0.1:5500). Явно вказані дозволені HTTP-методи та заголовки.
2. Додані базові security-заголовки у відповідь сервера:

X-Content-Type-Options: nosniff (заборона вгадування MIME-типів).

X-Frame-Options: DENY (захист від вбудовування сайту у фрейми/Clickjacking).

Referrer-Policy: no-referrer (захист від витоку URL-адрес).

Як протестувати проєкт локально
Запуск:

npm install (встановлення залежностей).

npm run dev (запуск бекенду).

Відкрити index.html фронтенду через Live Server (перевірити, щоб порт збігався з налаштуваннями CORS).

Приклади HTTP-запитів для тестування (cURL):

Тестування створення (з перевіркою авторизації):

Bash
curl -X POST http://localhost:3000/api/tickets \
-H "Content-Type: application/json" \
-H "X-Demo-UserId: 1" \
-d '{"theme":"Test SQLi: '\'' DROP TABLE Tickets; --", "priority":"Low", "status":"new", "description":"test"}'
Тестування IDOR (Спроба видалити чужу заявку):

Bash
curl -X DELETE http://localhost:3000/api/tickets/1 \
-H "X-Demo-UserId: 2" \
-v
# Очікуваний результат: HTTP 403/404 Error

Як перевірити сценарії (Test Cases)

1. **Як перевірити GET (Список):** Відкрийте сторінку фронтенду. Таблиця автоматично робить GET-запит на `/api/tickets` та завантажує список заявок. Переконайтеся, що дані відображаються.
2. **Як перевірити POST (Створення):** Заповніть форму на сторінці та натисніть "Створити". Заявка з'явиться в таблиці без перезавантаження сторінки. Або через cURL: `curl -X POST http://localhost:3000/api/tickets -H "Content-Type: application/json" -H "X-Demo-UserId: 1" -d '{"theme":"Тест", "status":"new", "priority":"Low"}'`
3. **Як перевірити помилку (400 Валідація):** Спробуйте відправити POST-запит (або форму) з порожнім полем "Тема". Фронтенд перехопить помилку 400 і покаже повідомлення "Тема є обов'язковою" без "падіння" додатку.
4. **Як перевірити помилку (Вимкнений бекенд):** Зупиніть роботу сервера (Ctrl+C в терміналі) і оновіть сторінку. Фронтенд покаже червоне повідомлення "Помилка мережі" замість пустого екрана.
5. **Як перевірити CORS:** Спробуйте зробити запит на API з іншого домену (або змініть порт Live Server з 5500 на інший). У консолі браузера з'явиться помилка `CORS policy`, оскільки бекенд жорстко дозволяє лише `http://127.0.0.1:5500`.
